4. Required prototype outcome
Required capability
Prototype standard
A. Entry / Start
A simple home/start experience that gets a user into the learning flow quickly. Guest/demo mode is acceptable.
B. 2D Xiangqi board
Playable board or a reliable loaded-game/demo flow. Legal move handling must not knowingly allow illegal Xiangqi moves.
C. Game record
Move history or equivalent state so a completed/demo game can be reviewed.
D. Engine/rules layer
A clear adapter boundary. Use a real Xiangqi engine if already available and legally/configurably usable; otherwise a clearly labeled demo/verified fallback must preserve the architecture.
E. Post-game review
Show 1–3 meaningful critical moments. Allow the user to navigate to a position and retry.
F. Reflection first
Before revealing the explanation, require the learner to give their own evaluation/intent/candidate move at an appropriate depth.
G. Grounded explanation
Explain WHAT changed, WHY the move/idea matters, and HOW the learner should think next time. All chess claims must come from verified structured inputs.
H. Practice follow-up
Recommend a related skill/theme puzzle or position; prefer unseen positions to exact repetition.
I. Spaced repetition
Store a due date / next review based on a transparent heuristic. Failures return sooner; independent transfer success returns later.
J. Learner dashboard
At minimum recent mistakes, skill progress/mastery, due reviews and recent activity.
K. Persistence
Use the simplest reliable persistence compatible with the repository. Local/dev persistence is acceptable for the prototype if migration path is documented.
L. Working launch
The app must start with documented commands. A human must be able to follow a 60–90 second demo path without reading source code.

6. Decision rules when something is missing
Missing / problem
Required response
No LLM API key
Implement an LLM provider interface and a deterministic/templated grounded demo provider. Keep the whole flow runnable. Clearly label it as demo/fallback.
No engine binary / engine setup fails
Keep an EngineAdapter boundary. Use an existing legally usable Xiangqi library/engine if present. Otherwise use a small verified demo analysis set and label it; do not pretend it is a real engine.
No production database
Use the simplest local/dev persistence compatible with the repo (for example SQLite or clean local persistence). Abstract it so production migration is possible; document the gap.
No login/auth
Use guest/demo identity. Do not block the learning loop on OAuth.
No large puzzle dataset
Create/use a very small legally safe demo bank with source metadata and verified solutions. Quality > quantity.
Existing repo is partially broken
Repair only what blocks the prototype. Preserve unrelated work. Document pre-existing failures separately.
Spec ambiguity
Choose the option that best preserves the core learning thesis and simplest maintainable architecture. Record the choice in a decision log.
Time pressure
Cut stretch features first: PvP, 3D, premium, animation, social/community, advanced ML. Do not cut the learning loop.
